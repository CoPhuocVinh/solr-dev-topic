B. Executive Summary

SolrCloud Topic Collection Resharding Plan

Vấn đề

  • Topic collection có thể tăng lên hàng chục triệu records, ví dụ khoảng 40M records, trong khi collection vẫn chỉ có numShards=1.
  • Một shard lớn dễ trở thành bottleneck cho query, indexing, recovery và vận hành SolrCloud.
  • Production có nhiều app/service gọi trực tiếp /solr/topic_xxx, nên v1 không giả định đổi app endpoint.
  • Cần cơ chế tự động phát hiện topic có total Mentions đạt ngưỡng cần chia shard sau đó tạo job xử lý reshard.

Mục tiêu

  • Tự động phát hiện topic có total Mentions đạt ngưỡng cần chia shard và reshard với downtime tối thiểu (~2–3s ở cutover), giữ nguyên endpoint để các app và service truy cập bình thường

Giải pháp tổng quan:

  • Publisher - detect job chạy định kỳ lúc 00:00 mỗi ngày để xác định topic cần chia shard.
  • Tính target_shards, insert job NEW vào DB, rồi push message vào queue data.resharding_solr_topic.
  • Consumer/worker xử lý job NEW/RUNNING/DONE, tạo template collection nếu cần, copy theo cursor, upsert buffer và save cursor sau upsert.
  • Worker requeue/resume khi copied đạt khoảng 1M docs/message.
  • Cutover bằng template swap: tái tạo collection đúng tên gốc từ index đã copy (reuse instanceDir), chỉ dùng alias tạm trong lúc swap.
  • Backup/snapshot original trước khi delete để rollback.

Details cách mới:

  4. Create Template Collection With New Shards

    • When: chỉ chạy nếu template collection chưa tồn tại.
    • Action: tạo template collection với số shard mới, ví dụ topic_100001_tmpl.
    • Note: template chỉ là collection tạm; cuối flow sẽ tái sử dụng index của nó để dựng lại collection gốc, không giữ template lâu dài.
    • Output: template collection sẵn sàng nhận upsert batch.

  5. Read Docs From Collection By Cursor

    • Action: query original collection theo cursor hiện tại rồi append docs vào upsert buffer.
    • Batch: 200 docs/query; ví dụ sau 50 queries buffer đạt 10,000 docs.
    • Notes: cursor có thể là cursorMark hoặc _version_ cursor tùy implementation.
    • Important: không copy field _version_ sang template.
    • Output: một batch docs từ original collection nằm trong buffer.

  6. Buffer >= 10,000 Docs?

    • YES: đi Upsert Batch To Target Collection.
    • NO: quay lại Read Docs From Collection By Cursor đọc tiếp; khi original collection hết docs thì flush nốt buffer cuối rồi mới đi tiếp.
    • Batch: 10,000 docs/upsert.

  7. Upsert Batch To Target Collection

    • Action: upsert toàn bộ docs trong buffer sang template collection (target khi copy).
    • Target: topic_100001_tmpl.
    • Important: không gửi _version_ từ original collection; Solr template tự sinh _version_ mới.

  8. Save Cursor

    • Action: sau khi upsert thành công, save cursor vào DB.
    • Important rule: chỉ save cursor sau khi upsert thành công; không save cursor ngay sau query để tránh mất data nếu worker chết trước upsert.

  9. Has More Docs?

    • YES: còn docs ở original collection, đi Copied >= 1M Docs?.
    • NO: original collection đã copy xong, đi Create Topic Alias để bắt đầu cutover.

  10. Copied >= 1M Docs?

    • Action: kiểm tra số docs đã copy trong message hiện tại.
    • YES: đi Push Message Back To Queue để requeue resume.
    • NO: quay lại Read Docs From Collection By Cursor để copy tiếp.
    • Threshold: 1M docs/message, tránh giữ một message quá lâu.

  11. Push Message Back To Queue

    • Queue: data.resharding_solr_topic.
    • Action: build resume message từ last_cursor đã save và push lại queue.
    • Status: job vẫn giữ RUNNING; lượt sau worker resume từ cursor đã lưu.

  12. Create Topic Alias

    • When: chạy sau khi copy xong (Has More Docs = NO).
    • Action: tạo alias tạm trỏ endpoint gốc sang template, ví dụ topic_100001 -> topic_100001_tmpl.
    • Mục đích: giữ endpoint /solr/topic_100001 vẫn phục vụ query/update từ template trong lúc dựng lại collection gốc.

  13. Delete Original Collection

    • Action: xóa physical collection gốc topic_100001 (đang bị alias tạm che, endpoint vẫn sống nhờ alias trỏ template).
    • Mục đích: giải phóng shard cũ để tái tạo lại collection cùng tên với số shard mới.

  14. Save Metadata InstanceDir Of Template Collection

    • Action: lưu lại instanceDir/dataDir của từng core template kèm mapping shard/hash-range.
    • Mục đích: để bước ADDREPLICA sau trỏ thẳng vào index đã build, không phải copy lại data lần nữa.

  15. UnLoad Template Collection (Drop Alias)

    • Action: unload các core của template (giữ nguyên file index trên disk theo instanceDir đã lưu, KHÔNG xóa dataDir) và drop alias tạm.
    • Mục đích: drop alias để giải phóng tên topic_100001, cho phép tạo lại collection cùng tên ở bước sau.
    • Lưu ý: từ lúc drop alias tới khi replica mới active là cửa sổ ngắn endpoint chưa phục vụ; nên làm nhanh và off-peak.

E. Implementation Detail

Implementation detail

E.1 Mục tiêu

Xây dựng cơ chế tự động reshard cho các topic collection trong SolrCloud 9 khi dữ liệu của một topic tăng vượt ngưỡng, ví dụ topic đạt khoảng 40 triệu records và numShards=1 không còn phù hợp.

    • Tự động detect topic lớn cần tăng shard.
    • Tạo template collection với số shard mới rồi tái tạo lại collection gốc từ index đã copy.
    • Migrate dữ liệu bằng cursor copy, upsert buffer và cursor progress lưu trong DB.
    • Resume an toàn khi worker requeue hoặc retry message.
    • Giữ endpoint cũ /solr/topic_xxx cho các app hiện tại (cùng tên collection gốc).
    • Cutover bằng template swap (reuse instanceDir); backup/snapshot original trước khi delete để rollback.

Constraint quan trọng: production có nhiều app/service đang gọi trực tiếp /solr/topic_xxx; vì vậy cutover phải giữ nguyên đúng tên collection gốc, chỉ dùng alias tạm trong cửa sổ swap rồi drop.

E.2 General Flow

Không chọn hướng split shard trực tiếp trên collection cũ làm flow chính. Hướng production an toàn hơn là tạo collection mới rồi migrate.

    1. Detect job chạy định kỳ, lấy topic collections và số shard hiện tại từ Solr.
    2. Query DB để bỏ qua collection đã có job active status NEW hoặc RUNNING.
    3. Tính targetShards = ceil(numDocs / 10M) cho candidate collections.
    4. Nếu cần reshard, insert job NEW rồi push message vào data.resharding_solr_topic.
    5. Worker consume message, load job từ DB và xử lý theo status NEW, RUNNING, DONE.
    6. Worker tạo template collection nếu chưa tồn tại, ví dụ topic_100001_tmpl.
    7. Worker đọc original collection theo cursor, append vào upsert buffer, upsert template và save cursor sau khi upsert thành công.
    8. Khi copied đạt khoảng 1M docs/message, worker requeue resume message và giữ job status RUNNING.
    9. Khi copy hết original collection, worker swap template về tên gốc (delete original → recreate createNodeSet=EMPTY → addreplica reuse instanceDir) rồi mark job DONE.

E.5 Worker Resume And Idempotency

    • Worker chỉ save last_cursor sau khi upsert buffer sang template thành công.
    • Nếu worker crash sau upsert nhưng trước khi save cursor, batch có thể được upsert lại; template phải idempotent theo unique key id.
    • Nếu message duplicate tới sau khi job đã DONE, worker load job từ DB và skip.
    • Nếu copied trong message hiện tại đạt khoảng 1M docs, worker build resume message, push lại queue và giữ job status RUNNING.
    • FAILED là terminal error status cho lỗi cần retry/manual intervention.

E.6 Optional No-Pause/Reconcile Risk

Đây là risk path tùy chọn, không phải main flow production v1. Nếu không pause write, các update rơi vào original sau khi cursor đã đi qua sẽ không có trong template; cần reconcile bù, không được blind upsert.

Vì cutover đã delete original và tái tạo cùng tên, không còn physical old để "hiện lại" bằng cách xóa alias. Rollback phải dựa vào backup/snapshot original chụp trước bước Delete Original.

F. Data Migration Mechanics

Cursor copy, upsert buffer, requeue

F.1 Read Original Collection By Cursor

    • Worker đọc original collection theo cursor hiện tại.
    • Batch size: 200 docs/query.
    • Cursor có thể là cursorMark hoặc _version_ cursor tùy implementation.
    • Nếu chọn _version_ cursor, sort theo _version_ asc,id asc.
    • Nếu dùng cursorMark, vẫn cần sort ổn định để resume không bị lệch.
    • Không copy _version_ sang template.
    • Chỉ copy stored fields khi dùng /select.
    • Copy fields/indexed-only fields được regenerate bởi schema template.
text

F.2 Upsert Buffer

    • Docs đọc từ original collection được append vào upsert buffer.
    • Khi buffer đạt 10,000 docs, upsert buffer sang template collection.
    • Nếu original collection hết docs và buffer cuối nhỏ hơn 10,000 docs, vẫn upsert buffer cuối.
    • Tên block nên là Upsert Buffer To Target Collection vì dùng cho cả batch đầy và batch cuối.

F.3 Save Cursor After Upsert

Chỉ save cursor sau khi upsert thành công. Không save cursor ngay sau query, vì nếu worker chết trước khi upsert thì có thể mất dữ liệu. Payload cursor xem ở bước Save Cursor mục D.2.

F.4 Requeue Threshold

    • Worker không giữ một message quá lâu.
    • Nếu copied trong message hiện tại đạt khoảng 1M docs, worker build resume message và push lại queue.
    • Job vẫn giữ status RUNNING; lần sau worker resume từ cursor đã lưu.

F.5 Deletes Handling

Cursor copy không bắt được hard delete nếu doc đã biến mất khỏi source trước khi worker đọc tới. Cần soft delete, tombstone table, change log từ DB/app hoặc cấm hard delete trong migration window.

H.1 SPLITSHARD Research

SPLITSHARD là Collections API built-in của Solr để split một shard hiện có thành các sub-shards nhỏ hơn.

text text

Cơ chế

    • Solr chia hash range của shard gốc thành các sub-ranges nhỏ hơn.
    • Documents trong shard gốc được phân phối sang sub-shards theo hash range mới.
    • Original shard vẫn giữ data as-is, nhưng sau split request được route sang sub-shards.
    • Sub-shards mới có số replica tương tự shard gốc.
    • Có thể chạy async và track bằng REQUESTSTATUS.
    • Dùng được cho collection tạo bằng numShards, tức hash-based routing như compositeId.
Pros Cons
Built-in trong Solr; không cần tự viết custom copy worker; không cần đổi app endpoint vì vẫn là cùng collection; Solr tự xử lý hash range split. In-place operation trên production collection; rollback khó hơn alias switch; không có target collection riêng; không giúp chuyển sang alias model; ít kiểm soát DB history, cursor progress và rollback policy; topic 40M docs có thể ảnh hưởng IO/CPU/recovery/latency.

Kết luận: SPLITSHARD đáng PoC/staging research; production chính vẫn nên dùng custom migration nếu cần DB history, cursor progress, alias rollback rõ hơn và chuyển sang alias model.

H.2 REINDEXCOLLECTION Research

REINDEXCOLLECTION là option built-in đáng research/PoC, nhưng không nên chọn làm production flow chính nếu topic vẫn nhận writes liên tục.

Pros Cons
Built-in trong Solr; có thể tạo target collection với shard mới; có thể hỗ trợ reindex/cutover qua alias. Source collection read-only trong lúc reindex; 40M docs có thể thành write pause dài; có thể lossy nếu field cần reindex không stored; ít kiểm soát copy cursor, DB history, resume và rollback hơn custom migration.

Kết luận: dùng cho PoC/staging research; production chính nên dùng custom migration nếu topic vẫn nhận writes liên tục.

J. Conclusion

Kết luận triển khai
    • Custom migration là hướng chính cho production v1 vì topic vẫn nhận writes liên tục.
    • Part 1 detect tạo job NEW trong DB rồi push message vào data.resharding_solr_topic.
    • Part 2 worker xử lý job NEW/RUNNING/DONE, copy theo cursor, upsert buffer, save cursor sau upsert và requeue để resume.
    • Cutover bằng template swap: copy sang template rồi tái tạo collection đúng tên gốc /solr/topic_100001, không giữ alias vĩnh viễn.
    • Mỗi lần reshard lặp lại flow này; không đẻ ra collection version _v2/_v3.
    • Duplicate message được skip khi job đã DONE.
    • Group alias cần audit trước/sau cutover, đặc biệt khi member vừa reshard đổi shard.
    • SPLITSHARD và REINDEXCOLLECTION chỉ nên dùng cho PoC/research trước khi cân nhắc production.
