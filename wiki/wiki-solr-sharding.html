B. Executive Summary

SolrCloud Topic Collection Resharding Plan
  • Tự động reshard topic collection trong SolrCloud 9 khi dữ liệu vượt ngưỡng, ví dụ topic đạt khoảng 40 triệu records.
  • Production có nhiều app/service gọi trực tiếp /solr/topic_xxx, nên v1 không giả định đổi app endpoint.
  • Hướng chính là custom migration: tạo target collection version mới, copy theo cursor, upsert buffer, save cursor progress, requeue/resume, rồi alias cutover.
  • Lần cutover đầu tiên giữ endpoint cũ bằng shadow alias; từ lần 2 trở đi update alias sang collection version mới.
  • Worker chỉ save cursor sau khi upsert thành công để resume an toàn và tránh mất data.
  • Giữ old collection theo retention policy để rollback.

D. End-to-End Flow

Detect/enqueue và worker/migration flow

D.1 Detect Resharding Topic Layer

  1. Schedule detect job

    • Action: job detect chạy định kỳ lúc 00:00 mỗi ngày.
    • Output: bắt đầu một detect run mới.
    • Notes: đây chỉ là detect/enqueue layer, chưa copy data.

  2. Get List Collection And Num Shards On Solr

    • Action: query Solr để lấy toàn bộ topic collections và số shard hiện tại.
    • Source: Solr Topic metadata.
    • Output: danh sách collection kèm num_shards.
    • Persist: có thể lưu snapshot collection list nếu cần audit detect run.
    json

  3. Query Active Jobs For Solr Collection List

    • Action: query MongoDB Resharding Job Collection theo collection list vừa lấy.
    • Filter: chỉ lấy job active với status NEW hoặc RUNNING.
    • Batch: chunk 1000 collections/query.
    • Output: set các collection đang có active job.
    javascript

  4. Classify Collections

    • Action: tách collection thành Active Job Collections và Candidate Collections.
    • Output: active job collections đi Skip Detect; candidate collections đi tiếp bước lấy numDocs.
    • Rule: collection đã có job NEW hoặc RUNNING thì không tạo job mới để tránh duplicate.

  5. Skip Detect For Active Job Collections

    • Action: bỏ qua detect cho collection đã có active job.
    • Output: không insert job mới, không push queue message mới.

  6. Get Num Documents Per Collection

    • Action: với candidate collections, query số docs từng collection.
    • Batch: 100 per request.
    • Output: danh sách candidate kèm num_shards và num_docs.
    json

  7. Check Need Reshard

    • Block: Is (Num Docs / 10M) <= CurrentShards?
    • Logic: targetShards = ceil(numDocs / 10M).
    • YES: targetShards <= currentShards, current shards đủ rồi, flow đi Skip Detect.
    • NO: targetShards > currentShards, collection cần reshard, flow đi insert job NEW.
    text 1 => cần reshard ]]>

  8. Insert Init Resharding Of Collection With Status NEW Into DB

    • Action: insert job mới vào MongoDB với status NEW.
    • Rule: insert job trước khi push queue để worker luôn load được job từ DB.
    json

  9. Build Message

    • Action: build payload gửi qua queue cho worker Part 2.
    json

  10. Push To Queue

    • Queue: data.resharding_solr_topic.
    • Action: push message vào queue.
    • Batch: 1 topic per message.
    • Output: worker Part 2 sẽ consume message và xử lý reshard.

D.2 Resharding Solr Topic Layer

  1. Consume Message From Queue

    • Queue: data.resharding_solr_topic.
    • Action: worker consume message.
    • Batch: 10 per handle or 30s.
    json

  2. Load Resharding Job From DB

    • DB: MongoDB Resharding Job Collection.
    • Action: load job record theo collection hoặc target_collection.
    • Read fields: status, collection, target_collection, last_cursor, target_shards, copied_count.

  3. Check Job Status

    • Status chính: NEW, RUNNING, DONE.
    • NEW: acquire job lock, set status sang RUNNING, rồi đi tiếp Check Target Collection Exists.
    • RUNNING: resume job đang xử lý dở, không skip, rồi đi tiếp Check Target Collection Exists.
    • DONE/status khác: skip duplicate message, không xử lý thêm.

  4. Check Target Collection Exists

    • Action: kiểm tra target collection đã tồn tại trên Solr chưa.
    • YES: target đã được tạo trước đó, đi tiếp copy data.
    • NO: tạo target collection với số shard mới, rồi đi tiếp copy data.
    text

  5. Read Old Collection By Cursor

    • Action: query old collection theo cursor hiện tại.
    • Batch: 200 docs/query.
    • Notes: cursor có thể là cursorMark hoặc _version_ cursor tùy implementation.
    • Important: không copy field _version_ sang target.
    • Output: một batch docs từ old collection.

  6. Append Docs To Upsert Buffer

    • Action: append docs vừa đọc vào upsert buffer.
    • Example: 200 docs/query, sau 50 queries thì buffer có 10,000 docs.

  7. Check Buffer >= 10,000 Docs

    • YES: upsert buffer sang target collection.
    • NO: check old collection còn docs không.
    • Rule: block upsert nên gọi là Upsert Buffer To Target Collection, vì dùng cho cả buffer đủ 10,000 và buffer cuối nhỏ hơn 10,000.

  8. Handle Buffer Not Full

    • Block: Has More Docs From Old Collection?
    • YES: quay lại Read Old Collection By Cursor.
    • NO: old collection hết docs, upsert buffer cuối dù nhỏ hơn 10,000 docs.
    text upsert 4,300 docs cuối ]]>

  9. Upsert Buffer To Target Collection

    • Action: upsert toàn bộ docs trong buffer sang target collection.
    • Target: topic_100001_v2.
    • Important: không gửi _version_ từ old collection; Solr target tự sinh _version_ mới.

  10. Save Cursor Progress To DB

    • Action: sau khi upsert thành công, save cursor vào DB.
    • Important rule: chỉ save cursor sau khi upsert thành công; không save cursor ngay sau query để tránh mất data nếu worker chết trước upsert.
    json

  11. Check Copied >= 1M Docs In This Message

    • Action: kiểm tra số docs đã copy trong message hiện tại.
    • YES: build resume message, push lại queue, job vẫn giữ status RUNNING.
    • NO: check old collection còn docs không; nếu còn docs thì tiếp tục copy trong cùng message, nếu hết docs thì đi alias cutover.
    json

  12. Build Messages Requeue And Push To Queue

    • Action: build resume message và push lại queue data.resharding_solr_topic.
    • Reason: worker không giữ một message quá lâu.
    • Threshold: 1M docs/message.

  13. Alias Already Exists?

    • Action: sau khi hết docs từ old collection, check alias topic đã tồn tại chưa.
    • NO: đây là lần init, create topic alias topic_100001 -> topic_100001_v2.
    • YES: đây là lần reshard sau, switch alias sang target collection, ví dụ topic_100001 -> topic_100001_v3.

  14. Mark Job DONE And Save Final Cursor

    • Action: sau khi alias create/switch thành công, update job DONE.
    • Output: job kết thúc; duplicate message sau đó sẽ bị skip vì job đã DONE.
    json

E. Implementation Detail

Implementation detail

E.1 Mục tiêu

Xây dựng cơ chế tự động reshard cho các topic collection trong SolrCloud 9 khi dữ liệu của một topic tăng vượt ngưỡng, ví dụ topic đạt khoảng 40 triệu records và numShards=1 không còn phù hợp.

  • Tự động detect topic lớn cần tăng shard.
  • Tạo collection version mới với số shard phù hợp hơn.
  • Migrate dữ liệu bằng cursor copy, upsert buffer và cursor progress lưu trong DB.
  • Resume an toàn khi worker requeue hoặc retry message.
  • Giữ endpoint cũ /solr/topic_xxx cho các app hiện tại.
  • Cutover bằng alias create/switch và giữ old collection để rollback.

Constraint quan trọng: production có nhiều app/service đang gọi trực tiếp /solr/topic_xxx; vì vậy lần cutover đầu tiên cần dùng shadow alias để giữ nguyên endpoint cũ.

E.2 General Flow

Không chọn hướng split shard trực tiếp trên collection cũ làm flow chính. Hướng production an toàn hơn là tạo collection mới rồi migrate.

  1. Detect job chạy định kỳ, lấy topic collections và số shard hiện tại từ Solr.
  2. Query DB để bỏ qua collection đã có job active status NEW hoặc RUNNING.
  3. Tính targetShards = ceil(numDocs / 10M) cho candidate collections.
  4. Nếu cần reshard, insert job NEW rồi push message vào data.resharding_solr_topic.
  5. Worker consume message, load job từ DB và xử lý theo status NEW, RUNNING, DONE.
  6. Worker tạo target collection nếu chưa tồn tại, ví dụ topic_100001_v2.
  7. Worker đọc old collection theo cursor, append vào upsert buffer, upsert target và save cursor sau khi upsert thành công.
  8. Khi copied đạt khoảng 1M docs/message, worker requeue resume message và giữ job status RUNNING.
  9. Khi copy hết old collection, worker create/switch alias rồi mark job DONE.

E.5 Worker Resume And Idempotency

  • Worker chỉ save last_cursor sau khi upsert buffer sang target thành công.
  • Nếu worker crash sau upsert nhưng trước khi save cursor, batch có thể được upsert lại; target phải idempotent theo unique key id.
  • Nếu message duplicate tới sau khi job đã DONE, worker load job từ DB và skip.
  • Nếu copied trong message hiện tại đạt khoảng 1M docs, worker build resume message, push lại queue và giữ job status RUNNING.
  • FAILED là terminal error status cho lỗi cần retry/manual intervention.

E.6 Optional No-Pause/Reconcile Risk

Đây là risk path tùy chọn, không phải main flow production v1. Nếu cần reconcile giữa source và target sau alias switch, không được blind upsert.

text topic_100001_v3 T3: doc A update tiếp vào topic_100001_v3 T4: reconcile copy bản doc A từ v2 sang v3]]>

_version_ của hai collection không so sánh trực tiếp được vì mỗi collection sinh version riêng.

text target.updated_at: overwrite else: skip]]>

Nếu updated_at không đáng tin, cần chọn application version/timestamp khác hoặc thiết kế change log riêng trước khi dùng no-pause reconcile.

E.7 Rollback

Nếu chưa có write mới vào topic_100001_v2, rollback init có thể delete shadow alias để physical old hiện lại.

text

Nếu target đã nhận writes mới, rollback về old có thể thiếu data. Khi đó cần replay write log, dual-write, reconcile ngược, hoặc quy định rollback window ngắn theo runbook.

F. Data Migration Mechanics

Cursor copy, upsert buffer, requeue

F.1 Read Old Collection By Cursor

  • Worker đọc old collection theo cursor hiện tại.
  • Batch size: 200 docs/query.
  • Cursor có thể là cursorMark hoặc _version_ cursor tùy implementation.
  • Nếu chọn _version_ cursor, sort theo _version_ asc,id asc.
  • Nếu dùng cursorMark, vẫn cần sort ổn định để resume không bị lệch.
  • Không copy _version_ sang target.
  • Chỉ copy stored fields khi dùng /select.
  • Copy fields/indexed-only fields được regenerate bởi schema target.
text

F.2 Upsert Buffer

  • Docs đọc từ old collection được append vào upsert buffer.
  • Khi buffer đạt 10,000 docs, upsert buffer sang target collection.
  • Nếu old collection hết docs và buffer cuối nhỏ hơn 10,000 docs, vẫn upsert buffer cuối.
  • Tên block nên là Upsert Buffer To Target Collection vì dùng cho cả batch đầy và batch cuối.

F.3 Save Cursor After Upsert

Chỉ save cursor sau khi upsert thành công. Không save cursor ngay sau query, vì nếu worker chết trước khi upsert thì có thể mất dữ liệu.

json

F.4 Requeue Threshold

  • Worker không giữ một message quá lâu.
  • Nếu copied trong message hiện tại đạt khoảng 1M docs, worker build resume message và push lại queue.
  • Job vẫn giữ status RUNNING; lần sau worker resume từ cursor đã lưu.

F.5 Deletes Handling

Cursor copy không bắt được hard delete nếu doc đã biến mất khỏi source trước khi worker đọc tới. Cần soft delete, tombstone table, change log từ DB/app hoặc cấm hard delete trong migration window.

F.6 Operational Constants

  • Read old collection: 200 docs/query.
  • Upsert buffer: 10,000 docs/upsert.
  • Requeue threshold: 1M docs/message.
  • Queue consume: 10 messages/handle or 30s.

H. Alternatives / Research

SPLITSHARD và REINDEXCOLLECTION

H.1 SPLITSHARD Research

SPLITSHARD là Collections API built-in của Solr để split một shard hiện có thành các sub-shards nhỏ hơn.

text text

Cơ chế

  • Solr chia hash range của shard gốc thành các sub-ranges nhỏ hơn.
  • Documents trong shard gốc được phân phối sang sub-shards theo hash range mới.
  • Original shard vẫn giữ data as-is, nhưng sau split request được route sang sub-shards.
  • Sub-shards mới có số replica tương tự shard gốc.
  • Có thể chạy async và track bằng REQUESTSTATUS.
  • Dùng được cho collection tạo bằng numShards, tức hash-based routing như compositeId.
Pros Cons
Built-in trong Solr; không cần tự viết custom copy worker; không cần đổi app endpoint vì vẫn là cùng collection; Solr tự xử lý hash range split. In-place operation trên production collection; rollback khó hơn alias switch; không có target collection riêng; không giúp chuyển sang alias model; ít kiểm soát DB history, cursor progress và rollback policy; topic 40M docs có thể ảnh hưởng IO/CPU/recovery/latency.

Kết luận: SPLITSHARD đáng PoC/staging research; production chính vẫn nên dùng custom migration nếu cần DB history, cursor progress, alias rollback rõ hơn và chuyển sang alias model.

text

H.2 REINDEXCOLLECTION Research

REINDEXCOLLECTION là option built-in đáng research/PoC, nhưng không nên chọn làm production flow chính nếu topic vẫn nhận writes liên tục.

Pros Cons
Built-in trong Solr; có thể tạo target collection với shard mới; có thể hỗ trợ reindex/cutover qua alias. Source collection read-only trong lúc reindex; 40M docs có thể thành write pause dài; có thể lossy nếu field cần reindex không stored; ít kiểm soát copy cursor, DB history, resume và rollback hơn custom migration.

Kết luận: dùng cho PoC/staging research; production chính nên dùng custom migration nếu topic vẫn nhận writes liên tục.

Kết luận triển khai
  • Custom migration là hướng chính cho production v1 vì topic vẫn nhận writes liên tục.
  • Part 1 detect tạo job NEW trong DB rồi push message vào data.resharding_solr_topic.
  • Part 2 worker xử lý job NEW/RUNNING/DONE, copy theo cursor, upsert buffer, save cursor sau upsert và requeue để resume.
  • Lần init dùng shadow alias để giữ nguyên endpoint /solr/topic_100001.
  • Từ lần 2 trở đi, worker switch alias sang collection version mới sau khi copy xong.
  • Duplicate message được skip khi job đã DONE.
  • Group alias cần audit trước/sau cutover, đặc biệt khi member là shadow alias.
  • SPLITSHARD và REINDEXCOLLECTION chỉ nên dùng cho PoC/research trước khi cân nhắc production.
