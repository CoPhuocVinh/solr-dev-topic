B. Executive Summary

SolrCloud Topic Collection Resharding Plan
  • Tự động reshard topic collection trong SolrCloud 9 khi dữ liệu vượt ngưỡng, ví dụ topic đạt khoảng 40 triệu records.
  • Production có nhiều app/service gọi trực tiếp /solr/topic_xxx, nên v1 không giả định đổi app endpoint.
  • Hướng chính là custom migration: tạo target collection version mới, full copy, delta sync, validate, rồi cutover.
  • Lần cutover đầu tiên giữ endpoint cũ bằng shadow alias; từ lần 2 trở đi update alias sang collection version mới.
  • Validate physical old vs physical new phải chạy trước cutover alias.
  • Giữ old collection theo retention policy để rollback.

D. End-to-End Flow

Detect/enqueue và worker/migration flow

D.1 Detect Resharding Topic Layer

  1. Schedule detect job

    • Action: chạy job theo schedule, ví dụ 00:00 mỗi ngày.
    • Output: tạo detect run cho ngày hiện tại nếu schedule enabled.
    • Persist: lưu detect run/state để lần chạy sau không enqueue trùng.

  2. Check active migration

    • Action: query DB history để kiểm tra topic hoặc detect run đang active.
    • Output: nếu có active run thì skip topic/run đó.
    • Persist: không tạo message mới khi topic đang migrate.

  3. List Solr collections

    • Action: gọi Collections API LIST hoặc đọc inventory nội bộ.
    • Output: danh sách candidate collections dạng topic_*.
    • Persist: lưu snapshot list collection nếu cần audit detect run.

  4. Filter active/current collections

    • Action: bỏ old version, target version đang migrate, inactive collection và collection không phải topic.
    • Output: danh sách active/current topic collections cần kiểm tra ngưỡng.
    • Persist: lưu skipped reason nếu cần debug detect.

  5. Get doc count and shard count

    • Action: lấy doc count bằng /solr/{collection}/select?q=*:*&rows=0&wt=json.
    • Action: lấy shard/router/health bằng CLUSTERSTATUS.
    • Output: có doc_count, current_num_shards, router và replica health.

  6. Calculate target shards

    • Action: tính target_num_shards = ceil(doc_count / target_docs_per_shard).
    • Output: topic qualify khi target_num_shards > current_num_shards.
    • Persist: lưu doc_count, current_num_shards, target_num_shards vào run candidate.

  7. Build queue message

    • Action: build payload cho topic cần reshard.
    • Output: message có topic_id, source_collection, doc_count, current_num_shards, target_num_shards, is_init.
    • Persist: gắn message với detect run để idempotent.

  8. Push to queue

    • Action: push vào queue data.resharding_solr_topic.
    • Output: 1 topic/message chờ worker xử lý.
    • Persist: mark candidate đã enqueue để tránh duplicate message.

D.2 Resharding Solr Topic Layer

  1. Consume queue

    • Action: worker nhận message từ data.resharding_solr_topic.
    • Output: lấy được topic reshard job với source collection và target shard count.
    • Persist: ack message chỉ sau khi run state đã được tạo hoặc resume an toàn.

  2. Lock and check run/version

    • Action: lock theo topic_id hoặc source_collection, rồi check DB run/version.
    • Output: tạo run mới hoặc resume run đang PAUSED.
    • Persist: lưu trạng thái run để chỉ một worker xử lý một topic tại một thời điểm.

  3. Create target collection

    • Action: tạo collection mới như topic_xxx_v2.
    • Output: target collection có shard count mới và sẵn sàng nhận writes từ migration worker.
    • Persist: lưu target_collection, configset/router/replication policy đã preserve từ source.

  4. Capture initial watermark

    • Action: lấy max(_version_) từ source trước full copy.
    • Output: có initial_watermark và last_watermark ban đầu.
    • Persist: lưu watermark vào DB run để delta sync resume được.

  5. Full copy by cursor

    • Action: query source bằng cursorMark, sort id asc, upsert vào target.
    • Action: không copy _version_ từ source sang target.
    • Output: target có baseline docs từ source.

  6. Persist cursor and requeue

    • Action: lưu full_copy_cursor, copied count và batch progress.
    • Output: nếu batch/run quá lớn thì set PAUSED và requeue.
    • Persist: worker có thể resume từ cursor cuối cùng nếu restart.

  7. Delta sync by _version_

    • Action: sync docs bằng query _version_:{last_watermark TO *].
    • Output: target bắt được insert/update phát sinh trong lúc full copy.
    • Persist: update last_watermark sau mỗi batch delta.

  8. Validate physical old vs physical new

    • Action: check count, sample ids, business queries/facets và shard/replica health.
    • Output: chỉ cho phép cutover khi validation pass hoặc nằm trong tolerance đã định nghĩa.
    • Persist: lưu validation result vào run history.

  9. Alias cutover

    • Action: chỉ chạy sau validate pass; init dùng shadow alias, các lần sau update alias.
    • Output: app đọc/ghi qua endpoint cũ nhưng traffic đi vào target collection mới.
    • Persist: lưu cutover_at và alias mapping sau cutover.

  10. Mark done and retain old

    • Action: set run DONE sau cutover thành công.
    • Output: migration completed, old collection vẫn được giữ để rollback.
    • Persist: lưu retention deadline cho old collection.

Note: diagram có thể biểu diễn alias cutover gần validate, nhưng runbook production phải enforce validate before alias cutover.

E. Implementation Detail

Implementation detail

E.1 Mục tiêu

Xây dựng cơ chế tự động reshard cho các topic collection trong SolrCloud 9 khi dữ liệu của một topic tăng vượt ngưỡng, ví dụ topic đạt khoảng 40 triệu records và numShards=1 không còn phù hợp.

  • Tự động detect topic lớn cần tăng shard.
  • Tạo collection version mới với số shard phù hợp hơn.
  • Migrate dữ liệu bằng full copy + delta sync.
  • Validate dữ liệu trước cutover.
  • Giữ endpoint cũ /solr/topic_xxx cho các app hiện tại.
  • Cutover an toàn bằng alias và giữ old collection để rollback.

Constraint quan trọng: production có nhiều app/service đang gọi trực tiếp /solr/topic_xxx; vì vậy lần cutover đầu tiên cần dùng shadow alias để giữ nguyên endpoint cũ.

E.2 General Flow

Không chọn hướng split shard trực tiếp trên collection cũ làm flow chính. Hướng production an toàn hơn là tạo collection mới rồi migrate.

  1. Nightly detect topic vượt ngưỡng.
  2. Tính số shard cần thiết.
  3. Tạo target collection version mới, ví dụ topic_100001_v2.
  4. Capture initial _version_ watermark.
  5. Full copy old -> new.
  6. Delta sync old -> new.
  7. Validate old vs new.
  8. Cutover bằng shadow alias hoặc alias switch.
  9. Reconcile nếu cần.
  10. Giữ old collection để rollback.

E.5 Cutover Modes

  • Strong consistency: pause write ngắn, final delta sync, validate nhanh, update alias, resume write.
  • Eventual consistency: delta sync đến khi backlog nhỏ, capture watermark, update alias, post-cutover reconcile source -> target, validate lại.

E.6 No-Pause Reconcile

Nếu không pause từ lần 2, bắt buộc phải reconcile cẩn thận. Không được blind upsert.

text topic_100001_v3 T3: doc A update tiếp vào topic_100001_v3 T4: reconcile copy bản doc A từ v2 sang v3]]>

_version_ của hai collection không so sánh trực tiếp được vì mỗi collection sinh version riêng.

text target.updated_at: overwrite else: skip]]>

Nếu updated_at không đáng tin, cần chọn application version/timestamp khác hoặc pause write ngắn.

E.7 Rollback

Nếu chưa có write mới vào topic_100001_v2, rollback init có thể delete shadow alias để physical old hiện lại.

text

Nếu target đã nhận writes mới, rollback về old có thể thiếu data. Khi đó cần pause write, replay write log, dual-write, hoặc reconcile ngược.

Sau full copy, sync các docs có _version_ > last_watermark từ source sang target.

F.4 Deletes Handling

_version_ không bắt được hard delete. Cần soft delete, tombstone table, change log từ DB/app hoặc cấm hard delete trong migration window.

F.5 Validate Physical Old Vs Physical New

  • Count source vs target.
  • Sample ids theo hash/range/random.
  • Business queries/facets quan trọng.
  • Shard/replica health.
  • Alias mapping.
  • Group alias impacted queries nếu topic nằm trong group alias.

G. Technical Context

Production state, schema, aliases

G.1 Current Production State

  • Mỗi topic đang là một physical Solr collection riêng, ví dụ topic_100001.
  • Collection dùng router.name=compositeId.
  • Collection dùng uniqueKey=id.
  • Ban đầu collection có thể chỉ có numShards=1.
  • Production hiện chưa có alias theo logical topic name.
  • Nhiều app/service read/write trực tiếp vào /solr/topic_100001.
  • Khi topic tăng dữ liệu lớn, một shard dễ trở thành bottleneck cho query/indexing.

H. Alternatives / Research

SPLITSHARD và REINDEXCOLLECTION

H.1 SPLITSHARD Research

SPLITSHARD là Collections API built-in của Solr để split một shard hiện có thành các sub-shards nhỏ hơn.

text text

Cơ chế

  • Solr chia hash range của shard gốc thành các sub-ranges nhỏ hơn.
  • Documents trong shard gốc được phân phối sang sub-shards theo hash range mới.
  • Original shard vẫn giữ data as-is, nhưng sau split request được route sang sub-shards.
  • Sub-shards mới có số replica tương tự shard gốc.
  • Có thể chạy async và track bằng REQUESTSTATUS.
  • Dùng được cho collection tạo bằng numShards, tức hash-based routing như compositeId.
Pros Cons
Built-in trong Solr; không cần tự viết full copy worker; không cần đổi app endpoint vì vẫn là cùng collection; Solr tự xử lý hash range split. In-place operation trên production collection; rollback khó hơn alias switch; không có target collection riêng để validate trước cutover; không giúp chuyển sang alias model; ít kiểm soát DB history, delta sync, reconcile và conflict policy; topic 40M docs có thể ảnh hưởng IO/CPU/recovery/latency.

Kết luận: SPLITSHARD đáng PoC/staging research; production chính vẫn nên dùng custom migration nếu cần rollback nhanh, validate trước cutover và chuyển sang alias model.

text

H.2 REINDEXCOLLECTION Research

REINDEXCOLLECTION là option built-in đáng research/PoC, nhưng không nên chọn làm production flow chính nếu topic vẫn nhận writes liên tục.

Pros Cons
Built-in trong Solr; có thể tạo target collection với shard mới; có thể hỗ trợ reindex/cutover qua alias. Source collection read-only trong lúc reindex; 40M docs có thể thành write pause dài; có thể lossy nếu field cần reindex không stored; ít kiểm soát delta/reconcile/history/rollback hơn custom migration.

Kết luận: dùng cho PoC/staging research; production chính nên dùng custom migration nếu topic vẫn nhận writes liên tục.

I.3 Research Checklist

  • Có chấp nhận shadow alias lần đầu không?
  • Pause write lần đầu được bao lâu?
  • Có hard delete trong migration window không?
  • updated_at có đáng tin cho conflict policy không?
  • Nếu updated_at không đáng tin, field/version nào là source-of-truth?
  • Group aliases hiện đang dùng logical topic names hay physical collection names?
  • Có app nào write vào group alias nhiều collections không?
  • Có cần ExactStatsCache cho query qua alias nhiều collections không?
  • SPLITSHARD có cần PoC trên topic_4777 hoặc staging để đo IO/latency/recovery không?
  • REINDEXCOLLECTION có thể PoC trên staging không?
  • DB history dùng DB nào?
  • Scheduler/worker runtime dùng gì?
  • Retention old collection là bao lâu?

J. Conclusion

Kết luận triển khai
  • Custom migration là hướng chính cho production v1 vì topic vẫn nhận writes liên tục.
  • Lần init dùng shadow alias + pause write mạnh để giữ nguyên endpoint /solr/topic_100001.
  • Từ lần 2 trở đi, cutover sạch hơn bằng cách update alias sang collection version mới.
  • No-pause cutover chỉ nên dùng khi reconcile có conflict policy đáng tin.
  • Group alias cần audit trước/sau cutover, đặc biệt khi member là shadow alias.
  • SPLITSHARD và REINDEXCOLLECTION chỉ nên dùng cho PoC/research trước khi cân nhắc production.
