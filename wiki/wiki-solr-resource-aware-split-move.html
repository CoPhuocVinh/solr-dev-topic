B. Tóm tắt

Vấn đề & giải pháp

Vấn đề: Khi split một shard, Solr đặt replica đầu tiên của mọi sub-shard lên đúng node đang giữ leader của shard cũ. Kết quả: sau split, một node ôm hết → node đó bị quá tải (hotspot).

Giải pháp: Sau split, chủ động trải các sub-shard ra node khác. Chọn node dựa trên tài nguyên thật của từng node (load, heap, GC, disk).

  • RF=1 (mỗi shard 1 bản): dời hẳn replica bằng MOVEREPLICA.
  • RF=2 (mỗi shard 2 bản): thường chỉ cần đổi node nào làm leader (REBALANCELEADERS), không dời data.

Concept split (rewrite vs link) và 3 cách phân tải: xem tài liệu SPLIT SHARD. Hướng tạo collection mới + alias: xem tài liệu Topic Collection Resharding.

E. Vì sao không dùng Placement Plugin / Autoscaling cho SPLITSHARD

Sao không để Solr tự đặt sub-shard cho đều?

Câu hỏi hợp lý: sao không để Solr tự đặt sub-shard cho đều, khỏi phải MOVEREPLICA tay? Vì cả 2 cơ chế "tự động" của Solr đều không làm được việc này.

E.1 Placement Plugin — chỉ lo bản phụ, không lo leader

Đọc source SplitShardCmd (Solr 9.8.1): bước "add initial replica to each sub-shard" ép node = node của parent leader (truyền node explicit → bỏ qua placement plugin). Chỉ bản phụ (khi RF>1) mới đi qua plugin.

Replica sub-shard Placement plugin?
Bản đầu (leader) mỗi sub-shard ❌ Ép về node parent leader
Bản phụ (chỉ có khi RF>1) ✅ Plugin chọn node

Hệ quả:

  • RF=1: chỉ có 1 bản = bản đầu bị ép → plugin không có gì để đặt → vô dụng → phải MOVEREPLICA.
  • RF=2: bản phụ được plugin trải, nhưng leader vẫn dồn node cũ → không giải quyết hotspot leader → phải REBALANCELEADERS.

Bản chất: placement plugin là quyết định "đặt ở đâu lúc TẠO", không phải "dời bản đã có". Nó không rebalance sau split được.

E.2 SolrCloud Autoscaling — Solr 9 không còn

  • Autoscaling framework (triggers nodeAdded/nodeLost/indexSize, policy, autoAddReplicas, UTILIZENODE, computeplan tự rebalance) đã bị GỠ ở Solr 9.0.
  • Solr 9 thay bằng Placement Plugin (chỉ lúc tạo — giới hạn ở E.1). Riêng phần trigger phản ứng (tự động làm gì đó sau sự kiện) thì bị gỡ và KHÔNG được thay thế.
  • → Trong 9.8.1 không có cơ chế "sau split tự động dời replica khỏi hotspot".

E.3 Kết luận

Cả 2 đều không dời được replica đã tồn tại sau split. Vì vậy phải tự làm: MOVEREPLICA (RF=1) + REBALANCELEADERS (RF=2). Đó chính là lý do tồn tại của flow này (mục I và J).

text node parent leader (ép, bỏ qua plugin) Placement Plugin -> chỉ chọn node cho BẢN PHỤ lúc tạo, không dời bản đã có Autoscaling -> đã gỡ ở Solr 9.0, không có trigger tự rebalance => Không cơ chế built-in nào trải sub-shard sau split => PHẢI tự MOVEREPLICA (RF=1) + REBALANCELEADERS (RF=2)]]>

F. Đo sức khỏe node

2 lưu ý quan trọng khi đo

F.1 Đo trực tiếp từng node, đừng qua VIP

Gọi /admin/info/system qua VIP chỉ trả về một node ngẫu nhiên do load balancer chọn → không biết đang đo node nào.

Cách đúng: lấy danh sách node từ CLUSTERSTATUS, rồi gọi thẳng vào base_url của từng node:

text /admin/info/system?wt=json GET /admin/metrics?group=node,jvm&wt=json # Kiểm tra field "node" trong response phải trùng node đang đo. # Node nào không gọi được -> đánh dấu bỏ, không chọn.]]>

F.2 Đừng tin "free RAM"

Field freePhysicalMemorySize là RAM trống thật sự (MemFree). Nhưng Solr để phần lớn RAM làm page cache cho index (điều này tốt), nên node khỏe vẫn báo free rất thấp.

text node HOÀN TOÀN KHỎE. => Nếu lọc "free RAM < 10% thì loại" thì loại nhầm cả 3 node staging -> kẹt.]]>

Thay bằng 2 chỉ số thật sự phản ánh memory:

  • heapLiveSet = heap còn dùng sau khi dọn rác (GC) / heap max. Lấy min của vài lần đo (vì heap lên xuống liên tục). Vượt 0.80 → loại.
  • gcRatio = % thời gian JVM dành cho dọn rác. Vượt 0.15 (15%) → node đang ngộp memory → loại.

Lý do 2 chỉ số này đúng: node khỏe và node ngộp đều báo free RAM ~1.5% (không phân biệt được), nhưng node ngộp thì heap cao sát max và GC chạy liên tục — 2 chỉ số này tách bạch rõ.

F.3 Các chỉ số cần lấy

Chỉ số Lấy từ đâu Nghĩa
load / số core info/system: systemLoadAverage, availableProcessors CPU bận
heapLiveSet metrics?group=jvm: memory.heap.used/max heap còn trống
gcRatio metrics?group=jvm: gc.*.time mức ngộp memory
disk trống metrics?group=node: CONTAINER.fs.usableSpace/totalSpace (bytes) còn chỗ chứa index
size index của replica metrics?group=core: INDEX.sizeInBytes để tính disk khi move

Đo 5 lần, cách nhau 15 giây, lấy giá trị median. Split có thể chạy lâu nên trước khi move phải đo lại (số cũ hết đúng).

H. Split shard

Kiểm tra -> split -> kiểm tra lại

H.1 Kiểm tra trước khi split

  • Split chạy trên node đang giữ leader → node đó phải khỏe (qua filter mục G). Không khỏe thì dừng.
  • Đủ disk: node leader phải còn trống ≥ 2.5 × size index (vì rewrite ghi lại index mới, cần hơn 2x).
  • Shard đang active, không có shard con thừa, không đang recovery.

I. RF=1: Move replica

Dời replica sang node khỏe

RF=1 chỉ có 1 bản mỗi shard, dồn hết trên node leader cũ. Dùng MOVEREPLICA để dời sang node khác. Move là copy data thật, nên phải chắc node đích đủ disk sau khi copy xong.

I.1 Cách chọn node đích

Node đích phải: khỏe (mục G) + chưa chứa replica của shard đó + đủ disk sau copy:

text = 20% # không đủ -> loại Trong các node đạt, chọn theo thứ tự: 1. node ít replica của collection này nhất (rải đều) 2. stressScore thấp nhất (khỏe nhất) 3. tên node (cho ổn định)]]>

I.2 Move từng cái một, đo lại mỗi lần

Move tuần tự, và đo lại tài nguyên trước mỗi lần move — vì lần move trước vừa làm node đích tốn disk + tăng tải.

text

I.3 Ví dụ: dời 2 replica ra khỏi hotspot

Split xong: shard1 (36GB) → shard1_0 (18GB) + shard1_1 (18GB). Cả 2 đang nằm trên staging3. Mỗi replica 18GB → cần 18 × 1.25 = 22.5GB. Mỗi node disk tổng 500GB.

Move #1 — dời shard1_0:

Node disk trống còn lại sau copy stress chọn?
staging1 200GB 35.5% (OK) 0.28
staging2 180GB 31.5% (OK) 0.24 ✔ (stress thấp hơn)

Move #2 — dời shard1_1 (đo lại): staging2 vừa nhận 18GB nên stress tăng lên 0.33 và đã có 1 replica.

Node disk trống còn lại sau copy stress số replica chọn?
staging1 200GB 35.5% (OK) 0.28 0 ✔ (ít replica hơn)
staging2 160GB 27.5% (OK) 0.33 1
text staging2, shard1_1 -> staging1. staging3 hết ôm 2 shard. Bài học: nếu KHÔNG đo lại giữa 2 lần move, move #2 vẫn tưởng staging2 khỏe nhất (số cũ) -> dồn cả 2 lên staging2. Nhờ đo lại + đếm số replica mới rải đều được.]]>

Nếu node stress thấp nhất nhưng không đủ disk sau copy thì vẫn loại. Disk luôn được ưu tiên hơn stress — node nhẹ mà không đủ chỗ chứa thì vô dụng.

J. RF=2: Đổi leader

Đã có 2 bản trên 2 node -> thường chỉ đổi leader

RF=2 đã có sẵn replica trên nhiều node. 2 cách, chọn 1:

Cách Làm gì Copy data? Khi nào
(a) Đổi leader REBALANCELEADERS Không Replica đã trải đều, chỉ cần chia lại vai trò leader. Nhẹ.
(b) Dời replica MOVEREPLICA (như mục I) Có Replica bị dồn node, cần trải lại data. Nặng.

J.1 Cách (a) — đổi leader

Chỉ đổi node nào làm leader, không dời data. Chọn leader là replica ACTIVE, loại PULL, chia leader đều các node khỏe.

text &replica=&property=preferredLeader&property.value=true # 2. bảo Solr cân lại leader: REBALANCELEADERS ...&collection=topic_100001&maxAtOnce=1&maxWaitSeconds=120 Ví dụ 4 shard con, 3 node -> chia leader 2/1/1.]]>

REBALANCELEADERS không chắc ăn 100%. Đã có report nó báo thành công nhưng leader không đổi. Nên:

  • Sau khi gọi phải kiểm tra lại leader có thật sự đổi chưa (ở gate cuối).
  • Nó tác động cả collection → trước khi gọi kiểm tra không có shard khác đang chờ đổi leader.
  • Không dùng FORCELEADER. Nếu mãi không đổi: restart replica đang làm leader để ép bầu lại (replica đánh dấu preferredLeader sẽ được ưu tiên) — ghi vào runbook.

J.2 Cách (b) — dời replica

Dùng MOVEREPLICA với cách chọn node y hệt mục I. Dùng khi replica thật sự bị dồn, cần trải lại data chứ không chỉ đổi leader.

K. Rollback & lỗi

Giữ shard cũ để lỡ có gì còn quay lại

K.1 Rollback: giữ shard cũ (xoá sau cùng)

Sau split, shard cũ chuyển inactive nhưng data vẫn còn trên disk (Solr không tự xoá). Với rewrite, index shard cũ không bị đụng → nó là bản snapshot tại thời điểm split.

text quay lại shard cũ (mốc lúc split). - Đánh đổi: mọi write SAU split nằm ở shard con, quay lại shard cũ sẽ mất -> chấp nhận. - Xong xuôi mới DELETESHARD shard cũ để lấy lại disk.]]>

Lưu ý: giữ shard cũ = tốn ~2x disk trong thời gian đó → chốt "giữ bao lâu" rồi mới xoá.

K.2 Bảng xử lý lỗi nhanh

Tình huống Làm gì
Split xong nhưng shard con thiếu / không active Dừng, không balance; cleanup có kiểm soát; không tự bật lại shard cũ
Move: replica mới chưa active Giữ bản cũ, chờ; chưa xoá bản cũ
Move: bản cũ mất mà bản mới không active Sự cố nghiêm trọng → xử lý tay ngay
Đổi leader: gọi xong leader không đổi Kiểm tra lại; retry; không FORCELEADER; cùng lắm restart leader cũ

L. Downtime

Read 0 downtime; write chỉ chớp sub-giây lúc đổi leader

Trả lời ngắn: flow này gần như không downtime. Read liền mạch tuyệt đối mọi bước. Write chỉ "chớp" sub-giây trên đúng shard đang đổi leader, retry được. Không có cutover 2–3s như template-swap.

L.1 Map downtime từng bước

Bước Read Write Ghi chú
Part 1: detect → queue → insert job NEW ✅ 0 ✅ 0 Chỉ đọc Solr + ghi Mongo, không đụng collection
Consume msg + lock job + set RUNNING ✅ 0 ✅ 0 Chỉ Mongo
SPLITSHARD ✅ 0 ✅ 0 Parent shard vẫn phục vụ read+write suốt; write được buffer sang sub-shard; switchover parent→inactive atomic
SPLIT GATE (verify) ✅ 0 ✅ 0 Chỉ đọc state
RF=1 MOVEREPLICA ✅ 0 ⚠️ chớp Blip sub-giây/sub-shard đúng lúc xoá leader cũ → bầu lại
RF=2 REBALANCELEADERS ✅ 0 ⚠️ chớp Blip sub-giây/sub-shard lúc bàn giao leader
FINAL GATE (verify) ✅ 0 ✅ 0 Chỉ đọc
DELETESHARD parent ✅ 0 ✅ 0 Parent đã inactive (không phục vụ) → xoá = giải phóng disk

L.2 Ba điểm cần nhớ

  1. Blip KHÔNG đến từ SPLITSHARD. Split zero downtime vì parent leader giữ vai tới lúc inactive, còn sub-shard leader (bản initial trên node cũ) đã active sẵn khi switch → write chỉ buffer, không rớt. Cái chớp chỉ đến từ bước rebalance sau split (MOVEREPLICA/REBALANCELEADERS). Tức là nếu không trải tải (chấp nhận hotspot) → downtime = 0 tuyệt đối. Blip chính là cái giá của việc phân tải.
  2. Blip cực nhỏ và bị khoanh vùng: chỉ WRITE (read liền mạch), chỉ đúng sub-shard đang đổi leader (1/N lượng write), chỉ ~sub-giây lúc bầu/bàn giao leader, và app có retry thì gần như không thấy.
  3. 10 pod KHÔNG cộng dồn downtime. Mỗi collection 1 endpoint riêng → blip của collection X không đụng Y → 10 pod = 10 blip nhỏ độc lập, không thành 1 downtime to. Nhưng degrade latency thì CÓ cộng dồn (10 rewrite + 10 recovery = bão IO/CPU chung cluster). → Khi scale pod, thứ phải sợ là latency, không phải downtime.

L.3 So với template-swap

Tiêu chí Template-swap Split + Move (flow này)
Read downtime ~2–3s cả endpoint 0
Write downtime ~2–3s cả endpoint Chớp sub-giây/shard, retry được
Nguồn downtime Cutover alias (bắt buộc) Chỉ từ rebalance (tuỳ chọn)
Endpoint Có lúc alias tạm Không đổi tên, không alias
10 pod Mỗi collection 1 cutover 2–3s Blip độc lập, không cộng dồn

L.4 Downtime budget 1 collection

text thực tế ~ 0. Không có cutover 2-3s như template-swap. Không đổi endpoint. Đổi lại: latency TĂNG lúc split/move (không downtime) -> chạy off-peak.]]>

2 thứ nên làm dù không có downtime: chạy off-peak (split rewrite + recovery làm tăng latency), và khuyến nghị app retry (app không retry có thể ăn 1–2 update fail đúng lúc "chớp" đổi leader).

  • Giữ shard cũ bao lâu rồi mới xoá?

N.2 Giải thích param hay nhầm

Param Nghĩa
waitForFinalState Param BẠN gửi. true = chờ replica mới active + recover xong mới trả về. Nên luôn bật.
waitForState Không phải param — là hàm nội bộ của Solr (zkStateReader.waitForState(...)) chờ cluster state khớp điều kiện, timeout 60s hardcode. Bạn không set được.
timeout Thời gian tối đa waitForFinalState chờ. Default 600s (10 phút). Index lớn recover lâu hơn → phải tăng.
async Chạy nền, trả về 1 request id → poll REQUESTSTATUS. Không có thì HTTP treo tới khi xong.
inPlaceMove Shared FS: dời bằng cách trỏ lại data dir, không copy. Local storage: vô hiệu → luôn copy + recover đầy đủ.
node / targetNode Chỉ định node → bỏ qua placement plugin. Không truyền thì plugin tự chọn.
type NRT (đọc+ghi realtime), TLOG (replay tlog), PULL (chỉ đọc, copy index). Khi move/add nên giữ đúng type như source.

N.3 Cạm bẫy vận hành (đọc kỹ)

  1. Timeout mặc định 600s + fail âm thầm. MOVEREPLICA/ADDREPLICA hết timeout mà replica mới chưa active thì không throw, chỉ ghi failure vào async result, không xoá source (để lại replica thừa trên target). Automation phải đọc async result, đừng coi completed là xong; và tăng timeout theo size index.
  2. ADDREPLICA / MOVEREPLICA KHÔNG check disk. Solr sẵn sàng copy tới khi đầy disk → disk projection ở app layer (mục I.1) là bắt buộc.
  3. ADDREPLICA waitForFinalState mặc định false → không set thì trả về khi core vừa tạo, chưa active. Luôn set true.
  4. Retry split bị chặn nếu sub-shard cũ đang ACTIVE. Split fail nửa chừng để lại sub-shard ACTIVE → lần split sau abort ("exists in active state") → phải dọn tay. Sub-shard inactive thì Solr tự dọn.
  5. SPLITSHARD tự check disk 2.0× (rewrite). Chỉ tắt được bằng sysprop solr.shardSplit.checkDiskSpace.enabled=false toàn cluster, không có param per-request. Ngưỡng 2.5× của pre-check (mục H.1) chặt hơn nên an toàn hơn.
